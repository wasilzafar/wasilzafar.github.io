From Theorem to Production State

A theorem may say that a sketch uses $O(\varepsilon^{-2}\log(1/\delta))$ counters and returns an estimate within a stated error. Production must decide what each counter stores, how bytes are laid out, which hash and seed define the state, what concurrent updates mean, and whether a snapshot created today can merge with one stored last year.

Think of a sketch as a measuring instrument. The mathematics is its measurement principle; the implementation is the calibrated device, connector, label, and maintenance log. A correct estimator inside an ambiguous, overflowing, or incompatible state is not dependable.

For a tiny example, an unsigned $8$-bit counter represents $0$ through $255$. Starting at $250$, ten increments should produce $260$. Wrapping produces $4$; saturation produces $255$. Neither silently preserves the unbounded-integer model. The component must choose a width and overflow policy, expose saturation, or prove the boundary cannot be reached.

A stable interface commonly offers update, query, merge, reset, and snapshot. Its real contract also specifies item encoding, weights, replay behavior, consistency, serialization, version compatibility, concurrency, failures, and observability.

A production sketch is a versioned state machine whose bytes, arithmetic, metadata, and operations must preserve the theorem’s assumptions. Big-O bounds do not specify overflow, serialization, replay, concurrency, or safe merge behavior.

From Theorem to Production State

Four unsigned 8-bit counters hold $[250,2,0,255]$. Apply $[+10,+3,+1,+1]$.

  1. Mathematical integers give $[260,5,1,256]$.
  2. Modulo-$256$ wraparound gives $[4,5,1,0]$.
  3. Saturation gives $[255,5,1,255]$ and should increment two saturation metrics.
  4. Checked arithmetic may reject atomically before committing.

Reflection: which policy best preserves the estimator, and what explicit signal is required for every alternative?

Schemas, Seeds, Versions and Numeric Widths

Model serialized state as $(h,p,b)$: header, semantic parameters, and payload. The header identifies magic, family, schema version, length, canonical byte order, flags, and checksum. Parameters record every field that changes interpretation: dimension, precision, register width, hash algorithm and seed identifier, item encoding, weights, estimator generation, and window.

Compatibility is not “deserialization succeeded.” It is a relation $C(S_1,S_2)$ derived from the merge theorem. Exact equality may be required for seeds and dimensions. Some formats permit a proved one-way conversion such as precision downsampling; the information loss must be explicit.

For a $w$-bit unsigned counter, maximum value is $2^w-1$. If cell mass is bounded by $U$, exact storage requires

$$ w\ge\lceil\log_2(U+1)\rceil. $$

Intermediate sums and products can require more width than stored cells. Floating-point paths must address rounding, NaNs, infinities, and reduction order. Packed layouts define bit numbering, boundaries, padding, alignment, and atomic updates. SIMD kernels must match a scalar reference for boundary values and supported architectures.

Versioning separates wire readability, merge compatibility, and query comparability. A reader may parse an old format yet be forbidden to merge it.

The central invariant is semantic identity: operations must interpret bytes under the same family, parameters, encoding, arithmetic, and randomness contract. Parsing is weaker than merge compatibility, and conversion is safe only when information loss is explicit and proved.

Merge Safety, Replay and Operational Invariants

Associativity permits regrouping compatible states; commutativity permits reordering when order is irrelevant. Neither provides idempotence. Replaying an additive summary counts its population twice even though merge code is mathematically correct.

Exactly-once effects require stable batch identity, provenance, and an atomic deduplication boundary. Registerwise maximum may be idempotent, but audit counters or privacy budgets may not be. Snapshots also need a consistency model: barriers, copy-on-write, double buffering, or version validation. Copying packed words during mutation can create a state that never existed.

Concurrency must preserve both cell arithmetic and global invariants. Atomic increments may work for independent cells; packed fields may need compare-and-swap loops. Merge during update needs exclusive ownership or synchronization.

Base additive state is $S=[5,4]$; batch B42 is $B=[3,2]$.

  1. One merge gives $[8,6]$.
  2. Retrying without deduplication gives $[11,8]$.

  4. Registerwise maximum is idempotent: $\max([5,1],[3,2])=[5,2]$, and replay remains $[5,2]$.

Rollouts, Monitoring and Sketch Incidents

Start with shadow exact answers for bounded populations. Compare accuracy, serialized round trips, replay, state size, and merge permutations. At scale, dual-write old and new versions, canary by region, treat seed/schema changes as epochs, reject unsafe cross-epoch merges, and preserve rollback readers.

Observe causes as well as estimates: state bytes, latency, saturation, overflow, NaNs, rejected merges, schema/seed distribution, snapshot age, replay rate, checksum failures, contention, audit divergence, and population lineage.

Incidents often masquerade as algorithmic error: retry doubles cardinality, mixed versions shift quantiles, SIMD diverges at boundaries, a snapshot misses concurrent writes, or a corrupt length allocates memory before validation.

Exact daily distinct counts are $[1000,2000,5000]$; sketch estimates are $[1012,1970,5075]$.

  1. Relative errors are $1.2\%$, $-1.5\%$, and $1.5\%$.
  2. All meet a $2\%$ audit threshold.
  3. Round-trip each state and require identical query and metadata.
  4. Replay one batch and verify payload or provenance-level idempotence.
  5. Try another seed and confirm rejection.

Success criteria: calculate errors, document population/window, pass round-trip/replay tests, and expose rejection metrics.

Production

Rollouts, Monitoring and Sketch Incidents: Practical Sketch Engineering

A telemetry platform processes $20$ million updates per second across $200$ regions. States live $18$ months, merge hourly, require p99 update latency below $5$ microseconds, total memory below $500$ GB, and audit error below $2\%$.

Design: bounded canonical wire format; immutable metadata; safe accumulation widths; scalar oracle and SIMD; batch ledger; epoch snapshots; compatibility matrix; dual-write canaries; stratified exact audits; and fail-closed merges.

Risks: mixed seeds, hot-cell saturation, retry replay, corrupt allocation, SIMD drift, torn snapshots, and high-cardinality metrics.

Evidence: golden cross-language vectors, property/fuzz tests, merge permutations, boundary arithmetic, crash injection, cross-CPU comparisons, benchmarks, shadow accuracy, memory forecasts, and recovery drills.

Decision: promote only after canaries meet accuracy, performance, and compatibility over a full merge/window cycle. Keep rollback readers and quarantine unknown required flags.

Write a Production Readiness Checklist

Connect each theorem assumption to a type rule, validation gate, test, metric, and incident response. Separate correctness from speed: establish scalar semantics and wire invariants first, then optimize cache layout, batching, allocation, and SIMD without changing behavior.

Practice

Practice: Write a Production Readiness Checklist

Design a mergeable service with update, query, merge, snapshot, and reset operations.

Tier 1 — Contract. Define item/weight domains, error semantics, consistency, replay, and ownership.

Tier 2 — Widths. For $U=10^9$, compute $\lceil\log_2(10^9+1)\rceil=30$ bits. Choose 32- or 64-bit storage and justify intermediates.

Tier 3 — Schema. Specify magic, family, version, flags, lengths, byte order, seed, precision, width, estimator generation, window, payload, checksum, and maximum allocation.

Tier 4 — Compatibility. Classify pairs as exact-compatible, explicitly convertible, query-comparable only, or incompatible.

Tier 5 — Failures. Trace wraparound, duplicate batch, torn snapshot, lost update, corrupt length, unsupported flag, and SIMD mismatch.

Tier 6 — Readiness. Produce SLOs, benchmarks, golden vectors, property/fuzz tests, rollout, dashboards, alerts, runbook, rollback, and owners.

Debugging prompts: doubled estimates suggest replay; one-CPU divergence suggests SIMD/endianness; hot-key error suggests saturation; memory spikes suggest unchecked lengths.

Stretch goal: define loss-accounted precision downsampling and prove when merge order remains equivalent.

Rubric (10 points): API 2; numeric/layout safety 2; schema/versioning 2; concurrency/replay 2; rollout/evidence 2.

Bridge: mergeable theory supplies algebra; robust/private streaming supplies adversary and leakage models. Engineering preserves both across bytes, threads, machines, upgrades, and failures.

Readiness checklist: freeze semantics before optimization; bound every width and allocation; canonicalize bytes; version meaning-changing parameters; reject unsafe merges; define replay and concurrency; compare scalar and SIMD; audit accuracy and lineage; canary full merge cycles; and rehearse rollback. Compact state is not ready until its assumptions are enforceable and observable.
