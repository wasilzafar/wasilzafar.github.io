Interval Scheduling: Minimum Meeting Rooms & Point Covering

September 10, 2026 Wasil Zafar 20 min read

Interval-scheduling problems share a family resemblance but not a single algorithm. This lesson covers the two members Part 16 left unimplemented: counting the minimum meeting rooms an overlapping schedule requires, and placing the fewest points that touch every interval on a line.

1. Introduction and Motivation

Interval-scheduling problems all start from the same raw material: a list of intervals, each with a start and an end. What differs is the question asked about them. Can you select a maximum set of mutually non-overlapping intervals? How many resources — rooms, servers, machines — are needed to host every interval at once, at the busiest moment? What is the smallest number of marker points such that every interval contains at least one marker? Each question has a genuinely different optimal-substructure shape, and each is solved by a greedy strategy that looks superficially similar — sort something, sweep left to right — but is safe for a different reason.

Part 16 of this curriculum already proved two members of this family correct: Activity Selection, which finds the maximum number of non-overlapping intervals by sorting on end time, and the closely related Maximum Non-Overlapping Intervals problem (LeetCode's erase_overlap_intervals), which asks the complementary question — the fewest intervals to remove so what remains never overlaps. Both are solved by the same sort-by-end-time greedy and share the same exchange-argument proof; this lesson does not re-derive them.

This lesson covers the two genuinely new members of the family that Part 16 introduced only conceptually: Minimum Meeting Rooms (also called Interval Partitioning), which asks how many simultaneous "slots" the intervals require at their busiest instant, and Interval Covering (minimum points to stab every interval), which asks for the fewest points that touch every interval. Neither reduces to "pick the largest non-overlapping subset" — meeting rooms is a counting problem about simultaneous overlap, and interval covering is a hitting-set problem — so each earns its own core insight and its own correctness argument.

2. Prerequisites

This lesson assumes you can sort a list of (start, end) pairs, use a binary min-heap (or your language's priority queue), and read an exchange-argument proof. Two pieces of the interval-scheduling family are treated here as already mastered rather than material to re-learn:

  • Activity Selection & the Exchange Argument (Part 16, section 4) proves — with a full exchange argument — that sorting by end time and always keeping the earliest-finishing compatible activity yields the maximum non-overlapping subset. The proof pattern used there (assume an optimal solution disagrees with greedy at the earliest point of disagreement, show the swap is safe, induct to the end) is the pattern this lesson leans on rather than repeats.
  • Interval Scheduling (Part 16, section 6, the erase_overlap_intervals function) is the complementary framing of the same sort-by-end greedy: instead of counting how many intervals you can keep, it counts the minimum number you must remove to eliminate every overlap.

If you have not read those two sections, do so before continuing — the correctness reasoning in this lesson assumes you already trust that proof and builds on top of it rather than repeating it. You do not need graph algorithms, dynamic programming, or amortized analysis here; a min-heap and a comparison sort are enough.

4. Minimum Meeting Rooms (Interval Partitioning)

Given $n$ meeting intervals, find the minimum number of rooms required so that no two meetings assigned to the same room overlap. This is also called interval partitioning: partition the intervals into the fewest groups such that no two intervals in the same group overlap.

A naive method scans every possible time instant between the earliest start and the latest end, and at each instant counts how many meetings are active by checking all $n$ of them. That costs roughly $O(n \cdot T)$ where $T$ is the size of the time range, and it does not even work when times are real-valued rather than a small bounded integer range. What actually matters is not every instant, but only the $O(n)$ instants where the active count can change — a meeting start or a meeting end.

Core insight: sort meetings by start time and maintain a min-heap of the end times of every room's currently assigned meeting. For each new meeting, in start-time order, check the room whose meeting ends soonest (the heap's minimum). If that meeting has already ended — its end time is at or before the new meeting's start — free that room and hand it to the new meeting: a pop followed by a push. Otherwise no room is free, so allocate a brand-new room: a plain push. Because the algorithm pushes exactly once per meeting and pops at most once per meeting, the heap's size can never decrease across the run, so its size at the very end already equals the running maximum — and that maximum is the minimum number of rooms required.

Plain-English Steps

  1. Sort meetings by start time, ascending.
  2. Push the first meeting's end time onto an empty min-heap.
  3. For each remaining meeting, in order: if its start time is at or after the heap's minimum end time, pop that minimum (its room is now free).
  4. Push the current meeting's end time onto the heap (occupying either the just-freed room or a brand-new one).
  5. After processing every meeting, the heap's size is the minimum number of rooms needed.

Pseudocode

min_meeting_rooms(meetings):
    sort meetings by start time ascending
    heap = empty min-heap
    push(heap, meetings[0].end)
    for each meeting in meetings[1 .. n-1]:
        if meeting.start >= peek_min(heap):
            pop_min(heap)              # earliest-freed room becomes available
        push(heap, meeting.end)        # occupy a room until this meeting ends
    return size(heap)

The full min-heap implementation below reproduces the worked-example trace above and returns 3.

import heapq

def min_meeting_rooms(meetings):
    """
    Minimum Meeting Rooms (Interval Partitioning)
    meetings: list of (start, end) tuples, end exclusive
    Time: O(n log n), Space: O(n) for the heap
    """
    if not meetings:
        return 0
    meetings = sorted(meetings, key=lambda m: m[0])
    room_ends = []  # min-heap of end times of occupied rooms
    heapq.heappush(room_ends, meetings[0][1])

    for start, end in meetings[1:]:
        if start >= room_ends[0]:
            heapq.heappop(room_ends)  # earliest-freed room becomes available
        heapq.heappush(room_ends, end)

    return len(room_ends)

# Worked example: five meetings, peak overlap of 3
meetings = [(1, 5), (2, 7), (4, 6), (6, 8), (8, 9)]
print("Minimum rooms needed:", min_meeting_rooms(meetings))  # 3

// Minimum Meeting Rooms (Interval Partitioning)
// Time: O(n log n), Space: O(n) for the heap
#include <vector>
#include <queue>
#include <algorithm>
#include <iostream>

int minMeetingRooms(std::vector<std::pair<int, int>> meetings) {
    if (meetings.empty()) return 0;
    std::sort(meetings.begin(), meetings.end());  // sorts by start, then end

    std::priority_queue<int, std::vector<int>, std::greater<int>> roomEnds;
    roomEnds.push(meetings[0].second);

    for (std::size_t i = 1; i < meetings.size(); ++i) {
        if (meetings[i].first >= roomEnds.top()) {
            roomEnds.pop();  // earliest-freed room becomes available
        }
        roomEnds.push(meetings[i].second);
    }
    return static_cast<int>(roomEnds.size());
}

int main() {
    std::vector<std::pair<int, int>> meetings{{1, 5}, {2, 7}, {4, 6}, {6, 8}, {8, 9}};
    std::cout << "Minimum rooms needed: " << minMeetingRooms(meetings) << '\n';  // 3
}

// Minimum Meeting Rooms (Interval Partitioning)
// Time: O(n log n), Space: O(n) for the heap
import java.util.*;

public class MinMeetingRooms {
    static int minMeetingRooms(int[][] meetings) {
        if (meetings.length == 0) return 0;
        int[][] sorted = meetings.clone();
        Arrays.sort(sorted, (a, b) -> a[0] - b[0]);

        PriorityQueue<Integer> roomEnds = new PriorityQueue<>();  // min-heap
        roomEnds.add(sorted[0][1]);

        for (int i = 1; i < sorted.length; i++) {
            if (sorted[i][0] >= roomEnds.peek()) {
                roomEnds.poll();  // earliest-freed room becomes available
            }
            roomEnds.add(sorted[i][1]);
        }
        return roomEnds.size();
    }

    public static void main(String[] args) {
        int[][] meetings = {{1, 5}, {2, 7}, {4, 6}, {6, 8}, {8, 9}};
        System.out.println("Minimum rooms needed: " + minMeetingRooms(meetings)); // 3
    }
}

Alternative: The Sweep-Line Count

An equivalent, non-heap way to find the same answer: record a $+1$ event at every meeting's start and a $-1$ event at every meeting's end, sort all $2n$ events by time, and scan through summing the running total. The running total at any instant is exactly the number of meetings alive at that instant, so its maximum over the whole sweep is the minimum room count. The only subtlety is tie-breaking: when a meeting ends at exactly the same instant another starts, the end event must be processed first, since a room freed at time $t$ is immediately reusable by a meeting starting at $t$ — sorting ties with $-1$ before $+1$ achieves this automatically.

def min_meeting_rooms_sweep(meetings):
    """
    Sweep-line alternative: +1 at every start, -1 at every end.
    Ties sort end-before-start, since a room freed at time t is
    immediately reusable by a meeting starting at t.
    Time: O(n log n), Space: O(n) for the event list
    """
    events = []
    for start, end in meetings:
        events.append((start, 1))
        events.append((end, -1))
    events.sort()  # (-1) sorts before (+1) at an equal time

    rooms = 0
    peak = 0
    for _, delta in events:
        rooms += delta
        peak = max(peak, rooms)
    return peak

meetings = [(1, 5), (2, 7), (4, 6), (6, 8), (8, 9)]
print("Minimum rooms needed (sweep line):", min_meeting_rooms_sweep(meetings))  # 3

5. Interval Covering (Minimum Points to Stab All Intervals)

Given $n$ closed intervals on a line, find the minimum number of points such that every interval contains at least one chosen point — equivalently, "stab" or "pierce" every interval using as few needles as possible.

Naming note: this is the same underlying greedy algorithm as LeetCode's "Minimum Number of Arrows to Burst Balloons," which a separate, parallel curriculum entry (#66, Interval Stabbing) covers under that arrows framing. Here the identical sort-by-end-and-skip-covered greedy is presented as interval covering / piercing: place the fewest points so that every interval contains at least one of them. If you have already read the arrows lesson, you already know this algorithm — this section gives it an independent worked trace under the covering framing.

A brute-force method could try every subset of candidate points — only interval endpoints are ever worth trying, since sliding a point strictly inside an interval without crossing another endpoint never changes which intervals it covers — and keep the smallest subset that covers everything. But checking all subsets of endpoints is exponential. A method is needed that builds the answer one point at a time and never has to reconsider a placement.

Core insight: sort intervals by end time. Walk through them in that order. Whenever the current interval is not yet covered by any point placed so far, place a new point exactly at that interval's end — the rightmost position still inside it — and continue. Placing the point at the interval's end, rather than anywhere else inside it, is what makes the point maximally useful: since intervals are processed in end-time order, every later interval's end is at least as large, so pushing the point as far right as possible inside the current interval can only pick up additional later intervals whose start happens to fall at or before that point — it never fails to cover anything a more-leftward point would have covered.

Plain-English Steps

  1. Sort intervals by end time, ascending.
  2. Initialize last_point to "none placed yet."
  3. For each interval in order: if its start is greater than last_point (not yet covered), place a new point at this interval's end and update last_point to that end.
  4. Otherwise the interval's start is at or before last_point, so it already contains the most recently placed point — skip it, no new point needed.
  5. Return the list of placed points; its length is the minimum count.

Pseudocode

min_points_to_cover(intervals):
    sort intervals by end time ascending
    points = []
    last_point = NONE
    for start, end in intervals:
        if last_point is NONE or start > last_point:
            last_point = end
            points.append(last_point)
    return points

def min_points_to_cover(intervals):
    """
    Interval Covering: minimum points to stab every closed interval
    intervals: list of (start, end) tuples, both endpoints inclusive
    Time: O(n log n), Space: O(k) for the k returned points
    """
    if not intervals:
        return []
    intervals = sorted(intervals, key=lambda iv: iv[1])

    points = []
    last_point = None
    for start, end in intervals:
        if last_point is None or start > last_point:
            last_point = end
            points.append(last_point)
    return points

intervals = [(1, 3), (2, 5), (4, 6), (6, 8), (9, 12)]
result = min_points_to_cover(intervals)
print("Points placed:", result)               # [3, 6, 12]
print("Minimum points needed:", len(result))  # 3

// Interval Covering: minimum points to stab every closed interval
// Time: O(n log n), Space: O(k) for the k returned points
#include <vector>
#include <algorithm>
#include <iostream>

std::vector<int> minPointsToCover(std::vector<std::pair<int, int>> intervals) {
    std::vector<int> points;
    if (intervals.empty()) return points;
    std::sort(intervals.begin(), intervals.end(),
              [](const auto& a, const auto& b) { return a.second < b.second; });

    bool havePoint = false;
    int lastPoint = 0;
    for (const auto& iv : intervals) {
        int start = iv.first, end = iv.second;
        if (!havePoint || start > lastPoint) {
            lastPoint = end;
            havePoint = true;
            points.push_back(lastPoint);
        }
    }
    return points;
}

int main() {
    std::vector<std::pair<int, int>> intervals{{1, 3}, {2, 5}, {4, 6}, {6, 8}, {9, 12}};
    auto points = minPointsToCover(intervals);
    std::cout << "Minimum points needed: " << points.size() << '\n';  // 3
    for (int p : points) std::cout << p << ' ';                        // 3 6 12
    std::cout << '\n';
}

// Interval Covering: minimum points to stab every closed interval
// Time: O(n log n), Space: O(k) for the k returned points
import java.util.*;

public class IntervalCovering {
    static List<Integer> minPointsToCover(int[][] intervals) {
        List<Integer> points = new ArrayList<>();
        if (intervals.length == 0) return points;
        int[][] sorted = intervals.clone();
        Arrays.sort(sorted, (a, b) -> a[1] - b[1]);

        Integer lastPoint = null;
        for (int[] iv : sorted) {
            int start = iv[0], end = iv[1];
            if (lastPoint == null || start > lastPoint) {
                lastPoint = end;
                points.add(lastPoint);
            }
        }
        return points;
    }

    public static void main(String[] args) {
        int[][] intervals = {{1, 3}, {2, 5}, {4, 6}, {6, 8}, {9, 12}};
        List<Integer> points = minPointsToCover(intervals);
        System.out.println("Minimum points needed: " + points.size()); // 3
        System.out.println("Points: " + points);                       // [3, 6, 12]
    }
}

Correctness (exchange argument). Consider the first interval, in end-time order, that is not yet covered when greedy is about to place its next point; greedy places that point at this interval's own end, call it $e$. Any optimal solution must also place some point inside this interval — say at position $p \le e$ — otherwise the interval would be left uncovered. Every not-yet-covered interval that $p$ covers has start $\le p \le e$, and because intervals are processed in increasing end-time order, that interval's own end is $\ge e$ — so it contains $e$ too (its start is $\le e$ and its end is $\ge e$). Replacing OPT's point $p$ with greedy's point $e$ therefore loses no coverage and can only gain coverage of later intervals whose start falls in $(p, e]$. Repeating this exchange, one point at a time, transforms any optimal solution into exactly greedy's point set without ever increasing its size — so greedy's count equals the optimum.

Why "Sort by End Time" Keeps Showing Up (and Where It Doesn't)

Interval Covering's exchange argument above has the same shape as Activity Selection's proof (Part 16, section 4): both sort by end time, and both show that committing as early as possible — the earliest-finishing activity, or a covering point pushed only as far as the current interval's own end — can never make later choices worse, only ever as good or better, because everything that follows sits at least as far to the right. When a family of greedy algorithms shares that shape, you do not need to rederive it from scratch each time; you need to identify which quantity plays the role of "the thing that, committed to as early as possible, only helps."

Minimum Meeting Rooms is a different animal. It does not select a subset of intervals or place covering points — it counts how many intervals are simultaneously alive at the worst moment, which is a question about overlap, not about end-time ordering (the heap approach in fact sorts by start time). Its correctness argument is a staying-ahead / exact-accounting argument rather than an exchange argument: the heap always holds exactly one end time per currently active meeting — never more, never fewer — so the heap's size at any instant is precisely the number of meetings alive at that instant. No algorithm can use fewer rooms than the maximum number of meetings ever alive simultaneously, since that many meetings are, by definition, pairwise overlapping and each needs its own room; the greedy heap process demonstrably reaches exactly that maximum and no higher. Matching a provable lower bound is its own correctness proof — different in shape from an exchange argument, but no less rigorous.

6. Complexity Comparison

All three approaches share the same $O(n \log n)$ time bound, dominated by sorting; they differ in what they hold in memory while sweeping.

Minimum Meeting Rooms — min-heap$O(n \log n)$$O(n)$ heap of room end times

7. Applications and Alternatives

Where these show up in real systems

  • Resource allocation: the minimum-meeting-rooms count is exactly the number of identical resources (rooms, rental cars, hospital beds) needed so that no request ever waits when its interval is otherwise satisfiable.
  • Classroom / room scheduling systems: university and conference-room schedulers use the same min-heap or sweep-line technique to answer "how many rooms must this campus have to run every requested class simultaneously without conflict."
  • CPU / network scheduling: the peak-overlap count models the minimum number of parallel execution units (cores, threads, network channels) needed so every task interval runs without contending for the same unit.
  • Sensor / monitoring placement (interval covering): placing the fewest checkpoints, cameras, or sampling instants so every reported time window is observed at least once is the same minimum-points problem.

Choose the min-heap when you also need to know which room each meeting is assigned to (the heap naturally tracks room identity alongside end time); choose the sweep line when you only need the count and want to avoid heap bookkeeping. Interval covering has no meaningful alternative structure beyond the sort-and-skip greedy — its simplicity is the point, and reaching for a heap or DP table here would be solving a harder problem than the one asked.

9. Summary Cheat Sheet

  • Interval-scheduling problems share raw material (intervals) but not one algorithm — each variant needs its own sort key and its own correctness argument.
  • Activity Selection and Maximum Non-Overlapping Intervals (Part 16) sort by end time and are proven by an exchange argument; this lesson does not repeat them.
  • Minimum Meeting Rooms sorts by start time and maintains a min-heap of room end times; the answer is the heap's peak size, which equals its final size because it never shrinks.
  • The sweep-line alternative counts $+1$ at every start and $-1$ at every end (ties: end before start); the running maximum is the room count.
  • Interval Covering sorts by end time and greedily places a point at the current uncovered interval's end, skipping everything that point already covers.
  • Meeting Rooms is proven correct by a staying-ahead / exact-accounting argument (heap size = simultaneous overlap, a matched lower bound); Interval Covering is proven correct by an exchange argument, the same shape as Activity Selection's.
  • All three run in $O(n \log n)$ time, dominated by sorting.
